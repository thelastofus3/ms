# Avatar Service

## Фотореалистический аватар из видео или фотографий

Основа приложения — **фотографический анимируемый Gaussian-аватар**. Рабочий просмотрщик использует пример HUGS; для личных фото реализовано отдельное хранилище. Следующий незавершённый этап — реальная реконструкция загруженного человека. Скелетный прототип больше не доступен в интерфейсе.

Подробности: [анализ решений](../../docs/research/2026-09-25-gaussian-human-video.md),
[план и журнал выполнения](../../docs/superpowers/plans/2026-09-25-gaussian-avatar-experiment.md),
[инструкции Gaussian-эксперимента](gaussian/README.md).

Проверено 26 сентября 2026:

- CLI принимает видео или набор фото, учитывает EXIF, ограничивает размер и число
  кадров, сохраняет JPEG и манифест с SHA256. Существующий результат не перезаписывается.
- Собран отдельный Docker-образ `avatar-hugs:86ebe55`: Python 3.8, PyTorch 1.13.1,
  CUDA 11.7. На RTX 2060 выполнены реальные CUDA-операции simple-knn, PyTorch3D
  и Gaussian rasterizer. Это проверка окружения, а не полного аватара.
- Из официальных архивов загружены данные `lab` и готовый checkpoint автора.
- Получены четыре рендера канонической внешности готового человека и статический
  Gaussian PLY: **531 701 Gaussian**, около **1,11 ГиБ занятой / 1,46 ГиБ
  зарезервированной памяти PyTorch** на RTX 2060. Это реальный прогон нейросетей
  checkpoint и renderer, но пока без движения и обучения на собственной съёмке.
  Команда `hugs_preview` работает без SMPL; запуск и пределы измерения описаны
  в [инструкции канонического preview](gaussian/README.md#3-canonical-checkpoint-preview-without-smpl).
  Локальные результаты: `.runtime/hugs-output/canonical-cli/` — `view-0.png` …
  `view-3.png`, `canonical.ply`, `report.json`, `verification.json`.
- Полный запуск HUGS с новыми позами требует `SMPL_NEUTRAL.pkl` и
  `SFU/0008/0008_ChaCha001_poses.npz` из AMASS. Они пока отсутствуют.

Быстрый старт из корня проекта:

```powershell
.venv/Scripts/python.exe -m avatar_service.capture C:/capture/person.mp4 .runtime/captures/person --fps 2 --max-frames 120
.venv/Scripts/python.exe -m avatar_service.capture C:/capture/photos .runtime/captures/person-photos
.venv/Scripts/python.exe -m avatar_service.hugs_runtime --data .runtime/hugs-data --checkpoint .runtime/hugs-checkpoint
```

Подготовленные кадры имеют статус `frames_only`: для восстановления собственного
человека ещё нужны маски, камеры, SMPL-fitting и адаптер данных. Gaussian-генератор
пока не подключён к API и браузерной анимации. API ниже продолжает выдавать skinned
GLB; загружаемые через него фотографии остаются фото-эталонами.

Проверки текущего этапа: **52 теста прошли**, 11 интеграционных проверок
PostgreSQL/Blender пропущены. CUDA-запуск и экспорт PLY проверены отдельно;
независимый review новых модулей завершён без оставшихся существенных замечаний.

## Текущая реализация

В браузере фотографический Gaussian-экран является основой приложения:
531 701 Gaussian из официального HUGS/lab, экспериментальная анимация 24 суставов,
пауза, выбор позы и локальный импорт PLY/SPLAT. MPFB убран из интерфейса и публичных
маршрутов; исходники прототипа сохранены отдельно. Для просмотра запустите из корня
`./scripts/prepare-gaussian-demo.ps1`, затем `cd apps/web; npm run dev` и откройте
http://127.0.0.1:5173. На этом компьютере пакет уже подготовлен.
Пример не требует PostgreSQL или запущенного Python-сервиса.

Раздел «Мои фотографии» принимает JPEG/PNG/WebP (1–32 фото, до 10 МБ и 24 Мп на
фото, до 100 МБ на набор). Есть предпросмотр, сохранение, история и удаление.
Запуск хранилища: `docker compose up -d --build avatar-photos`. Сервис слушает
127.0.0.1:8002; Vite проксирует `/v1/photo-captures`. Фото в отдельном Docker volume,
после нормализации без EXIF/GPS. HttpOnly cookie привязывает наборы к браузеру;
между устройствами учётная запись пока не синхронизируется. Не очищайте cookie,
если хотите сохранить доступ к наборам; ненужные фото удаляются через интерфейс.

**Создание личного аватара ещё не реализовано.** Набор имеет статус `photos_ready`,
не SUCCEEDED; запрос генерации возвращает 503, в интерфейсе причина видна до
загрузки. LHM++ GS-модели PixelShuffle/SMPLX-FREE повторно вернули 401 при запросе
config.json 26.09.2026; обычная LHMPP-700M вернула 200, но текущий upstream
Gaussian-экспортёр её не принимает. HUGS требует отдельной подготовки камер,
масок и поз/SMPL. Для завершения нужен работающий движок реконструкции и его
проверка на личной съёмке. Загрузка фото не заменяет эти этапы.

Это фотографическая внешность человека из набора авторов. Восстановление вашего
человека по съёмке и перенос движений с камеры ещё не подключены. При сильных
сгибах возможны артефакты приблизительной привязки; простой импорт TripoSplat
остаётся статическим. [Технические детали](gaussian/README.md).

Для продолжения в другом чате сохранены [состояние](../../docs/handoff/current.md)
и [готовый запрос](../../docs/handoff/resume-prompt.md).

Для отдельного Gaussian-эксперимента добавлены подготовка видео/фото, проверка
данных HUGS и изолированное CUDA-окружение. Команды и текущие ограничения:
[Gaussian experiment](gaussian/README.md). Подготовка кадров ещё не создаёт аватар.

FastAPI принимает профиль и фото-эталоны, PostgreSQL хранит очередь и метаданные, отдельный Python-воркер запускает изолированный Blender. Только валидированный результат становится доступен через API. При таймауте (240 с), ошибке или отмене успешный пакет не публикуется.

фотографии. Код закреплён на `4f88aaeb3629249fbbddb4d0784a06962d9e1338`.
Опубликованные веса (2,78 ГБ) и официальный архив prior-моделей (18,82 ГБ)
скачаны в `D:/CodexData/MasterProject/lhm`; отдельное окружение устанавливается
там же. `services/avatar/gaussian/lhm_smoke.py` — эксперимент с FP16 и выгрузкой
модулей на CPU между этапами. До успешного прогона он не включается в API
создания аватара. Проверка использует фото из набора автора, а не личные данные.
Результат и измеренная память будут записаны в отчёт эксперимента.

| Переменная | Значение по умолчанию |
|---|---|
| `AVATAR_DATABASE_URL` | `postgresql+psycopg://avatar:avatar-local@127.0.0.1:55432/avatar` |
| `AVATAR_DATA_DIR` | `.runtime/avatar-data` относительно рабочего каталога |
| `AVATAR_TOKENS` | обязательно: JSON `{"token":"owner-id"}` для API |
| `AVATAR_BLENDER` | локальный Blender из `scripts/bootstrap-avatar.ps1` |
| `AVATAR_MPFB` | `.tools/mpfb2/src` — каталог репозитория расширений Blender |
| `AVATAR_ASSETS` | `.tools/system-assets` |

API и воркер должны использовать одну БД и одинаковый абсолютный путь к данным. Для Linux задайте путь к Blender явно; Windows — проверенная платформа. SQLite используется только в быстрых тестах; рабочая очередь рассчитана на PostgreSQL.

В этой версии схема `avatar` создаётся при старте (`jobs`, `references`). Для обновления уже развёрнутой схемы с изменением колонок понадобится миграция; `create_all` не заменяет миграции.

## API

Все маршруты требуют `Authorization: Bearer <token>`. Чужие ресурсы возвращают 404. `AVATAR_TOKENS` — локальный адаптер авторизации; для общего приложения его заменит проверка учётной записи/токена платформы.

| Метод / маршрут | Назначение |
|---|---|
| `POST /v1/references` | JPEG/PNG до 10 МБ и 24 Мп, multipart `file`; нормализованный JPEG без исходных метаданных |
| `GET /v1/references/{id}` | Фото владельца |
| `POST /v1/avatar-jobs` | `{"profile":{...},"avatar_id":null}`; необязательный `Idempotency-Key` |
| `GET /v1/avatar-jobs/{id}` | QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED, ID аватара и версия |
| `POST /v1/avatar-jobs/{id}/cancel` | Отмена ожидающего или текущего задания |
| `GET /v1/avatars/{id}/versions/{n}` | Манифест успешного результата |
| `GET /v1/avatars/{id}/versions/{n}/model` | GLB |
| `GET /v1/avatars/{id}/versions/{n}/package` | ZIP с GLB и манифестом |
| `POST /v1/avatars/{id}/versions/{n}/approve` | Подтверждение внешности оператором-владельцем |

Повторный ключ с тем же запросом возвращает то же задание; с изменённым запросом — 409. Переданный `avatar_id` создаёт следующую версию только для владельца. Предыдущие версии сохраняются; подтверждение внешности относится к конкретной версии.

## Выполнение и восстановление

Воркер захватывает задание через `FOR UPDATE SKIP LOCKED`, получает уникальный ID попытки и аренду на 30 секунд. Каждую секунду он продлевает аренду; отмена или потеря владения прекращают Blender. После падения процесса другой воркер может повторить просроченное задание. Завершение проверяет ID попытки, поэтому устаревший воркер не перезапишет новый результат.

Blender пишет во временный каталог, затем проверяются GLB, контрольная сумма и карта костей, собирается ZIP, каталог переименовывается. Отдельная транзакция публикует путь результата только для действующей попытки. После аварийного завершения процесса могут оставаться неопубликованные временные каталоги; автоматическая сборка мусора пока не реализована. Они не доступны через API.

## Пределы первой версии

- Форма тела и три параметра лица задаются оператором. Узнаваемость требует реальных фото и проверки человеком.
- Разрешены один комплект одежды и короткая причёска либо отсутствие волос; материалы кожи/одежды/волос одноцветные PBR, глаза с текстурой. Это функциональный прототип, не фотореалистическая внешность.
- Есть базовые циклы ожидания/ходьбы; качество походки и возможные пересечения ткани требуют художественной доработки.
- Рост означает расстояние от подошвы до макушки тела в позе покоя; волосы могут увеличить видимый bounding box.
- Пакет проверяется структурно сервисом; дополнительный официальный Khronos glTF Validator доступен в `apps/web/scripts/validate-glb.mjs`.
- Реальные камеры, распознавание лиц, веб-конференция и Java-платформа ещё не подключены.
