# Цифровая комната: общий дизайн

**Изменение требований 27 сентября:** аватар должен быть фотографическим и
восстанавливаться по коллекции фото либо видео. Первоначальный выбор MPFB,
приоритет анимации над фотореализмом и GLB-проверка ниже заменены
[актуальной спецификацией аватара](2026-09-27-photographic-avatar-design.md).
Остальные контракты встречи и трекинга сохраняются.

Дата: 2026-09-23.

Статус: архитектура согласована в разговоре; письменная спецификация представлена для проверки перед планированием реализации. Документ описывает целевое поведение, а не существующее приложение.

## 1. Назначение

Дать физическим и удалённым участникам общее пространство для встречи. Физические люди находятся в комнате, камера фиксирует их движения, а удалённые участники наблюдают их аватары с произвольного ракурса в реалистичной цифровой копии комнаты. Удалённые участники перемещаются своими аватарами мышью и клавиатурой. Телевизор в физической комнате показывает видеоконференцию; его виртуальный аналог показывает те же выбранные медиапотоки.

Первая версия должна стать основой дальнейшего продукта. Алгоритмы реконструкции, создания внешности и оценки поз заменяются через адаптеры, без изменения идентичности участников и правил работы встречи.

## 2. Принятые требования

| Область | Решение |
|---|---|
| Масштаб | Одна комната/зал, 2 физических и 3 удалённых участника |
| Камеры | Одна фиксированная обычная RGB-камера; в модели данных предусматривается несколько |
| Реализм комнаты | Gaussian Splatting по фотографиям или видео |
| Геометрия | Отдельные пол, стены, препятствия и поверхности экранов |
| Аватар | Узнаваемая внешность, пригодность для скелетной анимации важнее фотореализма |
| Первый генератор аватаров | Blender + MPFB; фото-эталоны и уточнённый оператором профиль |
| Идентификация | Автоматическое сопоставление с зарегистрированными участниками, подтверждение оператором при сомнении |
| Управление | Физический человек — камера; удалённый — клавиатура и мышь |
| Экраны | Видеоконференция и демонстрация экрана; вид 3D-комнаты на телевизоре не входит в первую версию |
| Стек | Java/Spring Boot, React/TypeScript, Python, PostgreSQL, LiveKit |
| Оборудование | Тестовый компьютер: RTX 2060 6 ГБ VRAM, около 32 ГБ RAM |
| Развёртывание | Сначала локально; генераторы можно перенести на более мощный сервер |

Выбор видеоконференции для телевизора первоначально был допущением после пропущенного ответа, затем вошёл в согласованную архитектуру.

## 3. Границы

В первую версию входят: генерация и скачивание ресурсов, ручная разметка сцены, калибровка камеры, регистрация участников, сопровождение двух людей, основные движения тела, общая 3D-встреча, видеоконференция и режим телевизора.

Не входят: точные пальцы и мимика, физическая симуляция одежды, обновление мебели по камере, несколько помещений, автоматическая калибровка без опорных данных, слияние нескольких камер, гарантированное узнавание при закрытом лице, полностью автоматический фотореалистичный аватар из любого фото. Возможность расширения контрактов не означает реализацию этих функций.

## 4. Компоненты и владение данными

| Компонент | Ответственность | Владеет |
|---|---|---|
| Web | Редактор и 3D-встреча, управление, настройка аватара, телевизор | Временное состояние UI |
| Platform | Авторизация, пользователи, встречи, связь человека/аватара/медиа, каталог ресурсов, синхронизация | Схема PostgreSQL `platform` |
| Space Service | Загрузка исходных данных, реконструкция, упаковка пространства | Схема `space`, задания и выходные файлы пространства |
| Avatar Service | Сборка внешности и скелета, экспорт и проверка аватара | Схема `avatar`, задания и выходные файлы аватара |
| Tracking Agent | Захват кадров, калибровка, сопровождение, поза, наблюдения идентичности | Локальный профиль камеры; временные треки |
| LiveKit | WebRTC-аудио, видео и демонстрация экрана | Временные медиасессии |

Один сервер PostgreSQL допустим на старте, но сервисы не изменяют чужие схемы напрямую. Platform обращается к генераторам через HTTP API. Для первого масштаба достаточно сохраняемой в PostgreSQL очереди заданий каждого генератора; отдельный брокер не требуется.

Файлы обслуживаются по HTTP владельцем ресурса. Клиенты и соседние сервисы используют `assetId`, ссылку и контрольную сумму, а не абсолютный путь на диске. При переносе сервиса его файловый адаптер может работать с объектным хранилищем. Временные ссылки и служебные токены не включаются в скачиваемый пакет.

## 5. Два независимых потока

**Подготовка:** загрузка → сохраняемое задание → генерация → проверка → пакет → настройка/разметка → публикация версии ресурса.

**Встреча:** камера → Tracking Agent → Platform → подписанные на встречу клиенты. Видео/звук идут через LiveKit. Файлы сцены и аватара загружаются один раз и повторно используются; генератор не запускается на каждом кадре.

На текущем компьютере подготовка GPU-ресурсов и рабочая встреча не выполняются одновременно. На отдельном сервере это ограничение может быть снято настройкой размещения.

## 6. Общие контракты

Контракты публикуются с `schemaVersion`. Несовместимая основная версия отвергается с понятным сообщением; неизвестные необязательные поля могут игнорироваться. Обновление ресурса создаёт новую версию. Активная встреча закрепляет версии пространства, калибровки и аватаров.

### Координаты

- Метры, правая система, ось Y вверх; оси X и Z лежат в плоскости пола, X × Y = Z. В позе покоя человек смотрит вдоль +Z. Анатомические стороны задаются именами костей, а не знаком мировой координаты X.
- Вращения — нормализованные кватернионы `[x, y, z, w]`; при нулевой норме сообщение отклоняется.
- Мировое положение и вращение задаются отдельно от локальных вращений костей.
- Повороты костей измеряются относительно родительской кости. Матрицы исходной позы и карта костей поставляются в пакете аватара.
- Преобразование из OpenCV/реконструктора в координаты сцены выполняется адаптером один раз. Клиент не исправляет оси эвристически.

### Идентичность

- `userId` — зарегистрированный пользователь.
- `participantId` — присутствие пользователя в конкретной встрече; им же связываются медиапоток и аватар.
- `trackId` — временный трек камеры, не постоянная личность. Его область уникальности включает запуск агента и `cameraId`.
- `avatarId` и версия — ресурс внешности; смена внешности не меняет личность.
- `cameraId`, `calibrationVersion`, `spaceVersion` — происхождение координат наблюдения.

Публичный поток поз не содержит фото лица и биометрических шаблонов. Предположение агента о личности не даёт прав доступа к встрече.

### Пакет пространства

Архив с манифестом, визуальным представлением (`gaussian-ply` в первой версии), описанием масштаба и преобразования координат, геометрией пола и препятствий, точками входа и поверхностями экранов. В сырой реконструкции неизвестный масштаб отмечается явно; использовать такой пакет для трекинга до привязки запрещено.

### Пакет аватара

Архив с манифестом, GLB с текстурами и skinning, ростом, исходной позой, картой семантических костей и возможностями анимации. Обязательны таз, позвоночник, грудь, шея, голова, плечи/руки/кисти, бёдра/голени/стопы с явным различием сторон. Неизвестные вспомогательные кости остаются внутренней деталью модели.

### Наблюдение и публикуемая поза

Агент отправляет `TrackObservation`: источник, время захвата, номер последовательности, временный трек, оценку мирового положения и позы, уверенность и кандидата личности. Platform назначает подтверждённый `participantId` и публикует `PoseFrame`.

Platform проверяет принадлежность источника комнате, версию калибровки, конечность чисел, порядок кадров и назначение участника. Старые кадры не откатывают состояние. Очереди ограничены: при перегрузке сохраняются свежие данные, а не накапливается задержка.

## 7. Публикация и сбои

Задание имеет состояния `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELLED`. Отмена `RUNNING` сначала фиксируется запросом, затем подтверждается после остановки дочерней обработки. `SUCCEEDED` означает успешную генерацию и проверку пакета, но не его пригодность для встречи без последующей разметки.

Ресурс пространства проходит `DRAFT` → `ALIGNED` → `PUBLISHED`. Публикация разрешена только при известном масштабе, проверенном полу, границах перемещения, точке появления и корректной геометрии экранов. Аватар публикуется после проверки скелета и визуального просмотра оператором.

Результат публикуется атомарно после проверки файлов и манифеста. Временные файлы не выдаются как успешный результат. При перезапуске сервиса оставшееся задание получает диагностируемое состояние и может быть повторено; прежняя опубликованная версия сохраняется.

Отдельно диагностируются: неподходящие входные данные, недостаток памяти, недоступность зависимости, ошибка реконструкции, некорректный пакет и устаревшая калибровка. Нехватка памяти не подменяется демонстрационной сценой.

## 8. Развёртывание и доступ

Локальный агент получает камеру на Windows. Вычислительные генераторы изолируются от его окружения; для CUDA-конвейера предусматривается Linux/WSL2. Java, PostgreSQL и LiveKit могут запускаться рядом. Web имеет режим обычного участника, оператора и экрана телевизора.

Доступ к камере и регистрация лица выполняются явно в интерфейсе. Исходное видео трекинга по умолчанию не сохраняется; для эксперимента оператор может отдельно включить запись. Удаление профиля участника удаляет связанные эталонные данные распознавания. Служебные токены хранятся в конфигурации окружения, не в репозитории.

Локальная проверка проводится в доверенной сети. Для внешнего подключения требуются HTTPS/WSS, настроенный LiveKit/TURN и проверка прохождения медиа между разными сетями. Локальный успех не считается доказательством интернет-доступности.

## 9. Порядок реализации

1. Проверка наиболее рискованных стыков: локальная реконструкция небольшого скана, GS + анимируемый GLB в одном кадре, калиброванное движение одного человека.
2. Контракты, долговечные задания, файлы и редактор пространства.
3. Генератор аватара, перенос поз, два физических участника и идентификация.
4. Общая встреча, удалённое перемещение, LiveKit и телевизор.
5. Полный сценарий, восстановление после сбоев, измерение показателей и воспроизводимый запуск.

Каждая подсистема описана отдельной спецификацией и получает отдельный план с проверками. Необходимые прототипы алгоритмов сохраняются как эксперименты до подтверждения критериев; рабочие контракты не привязываются к их внутренним форматам.

## 10. Приёмка

| Проверка | Условие успеха |
|---|---|
| Генерация пространства | Один эталонный скан обработан на RTX 2060 6 ГБ без исчерпания памяти; пакет открывается после перезапуска |
| Внешний вид | Комната узнаваема с заранее выбранных контрольных ракурсов; дефекты отмечены в отчёте |
| Пространство | Масштаб, пол, границы, основные препятствия и экран соответствуют измерениям |
| Аватар | Узнаваемая внешность подтверждена оператором; GLB проходит тест движений без перепутанных сторон |
| Положение | На контрольных точках, при видимых стопах и корректной калибровке, ошибка ≤ 30 см |
| Скорость | Активный 3D-клиент: целевые 30 FPS; поза: ≥ 15 обновлений/с; задержка capture-to-render p95 ≤ 400 мс в LAN |
| Идентичность | В тестах пересечения/поворота/выхода нет молчаливого назначения чужого аватара; сомнение явно отражено |
| Встреча | 2 физических + 3 удалённых участника видят согласованную сцену |
| Медиа | Физический и виртуальный экраны показывают заданную конференцию/демонстрацию, без дублирования звука |
| Восстановление | Потеря камеры/сети, старые кадры и перезапуск генератора не повреждают опубликованные ресурсы |

Измерять на опубликованной версии сцены, при отключённой генерации. Записывать разрешение клиента и камеры, число Gaussian-точек, версии ПО, загрузку CPU/GPU, доступную VRAM, сеть и число клиентов. Показатели считаются подтверждёнными только после эксперимента; текущая спецификация не заявляет достижение этих чисел.

Для capture-to-render при разных устройствах синхронизировать часы либо измерять внешней видеозаписью. Время прихода сообщения не подменяет время захвата.
